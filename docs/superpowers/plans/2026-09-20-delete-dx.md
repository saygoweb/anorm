# Delete Developer Experience Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make deleting a record safe and first-class — bind the id, give `Model` a `delete()` / `deleteOrThrow()` pair and a `mapper()` accessor, and let a lifecycle listener see deletions.

**Architecture:** Five sequential tasks. Task 1 is a standalone security fix to `DataMapper::delete()`. Task 2 adds an opt-in `DeleteListenerInterface` and wires the event and snapshot clearing into the mapper. Tasks 3–5 add the `Model`-level API (`mapper()`, `delete()`, `deleteOrThrow()`) and update the docs that currently point consumers at `$_mapper`. Every task is TDD: failing test, minimal implementation, green, commit.

**Tech Stack:** PHP 7.4-compatible syntax, PHPUnit 9, MySQL via `Anorm\Test\TestEnvironment`, phpcs (PSR-12 + `phpcs.xml`), phpstan level 5.

**Spec:** `docs/superpowers/specs/2026-09-20-delete-dx.md`

## Global Constraints

- **PHP 7.4 syntax only in `src/`.** `composer.json` requires `^7.4 || ^8.0`. No constructor property promotion, no enums, no `readonly`, no `match`, no PHP 8 string functions (`str_contains`, `str_starts_with`).
- **Nullable typed parameters are fine** (`?Model $model = null`), they are 7.1+.
- **phpcs:** PSR-12 plus `phpcs.xml` — 150 char lines in `src/`, 200 in `test/`, short array syntax only.
- **phpstan:** level 5 over `src/` and `test/`.
- **Errors go to `error_log`**, never a `LoggerInterface`.
- **Test class naming:** file `Xxx_Yyy_Test.php`, class `XxxYyyTest` (see `test/anorm/DataMapper_Crud_Test.php`). Tests under `test/anorm/Lifecycle/` use plain PSR names (`ChangeListenerTest`).
- **`$_mapper` must keep working.** Every change is additive; no existing call site may break.
- **Verification after every task:** `composer test:quick && composer cs:check && composer analyze`.

### Task 2: `DeleteListenerInterface` and the delete event

> **As built.** Step 5 below wires the event off `self::$changeListener` with an
> `instanceof` test. That does not work: `setChangeListener()` is type-hinted to
> `ChangeListenerInterface`, so a delete-only listener cannot be registered at
> all. The implementation added a second static slot instead —
> `DataMapper::setDeleteListener()` / `getDeleteListener()` — and `notifyDelete()`
> reads that. See §3.3 of the spec for the reasoning. The tests register on the
> delete slot accordingly, and one extra test covers registering a listener that
> does not implement `ChangeListenerInterface`.

Deletes become visible to lifecycle listeners, and a deleted model stops
carrying a stale snapshot.

<?php

namespace Anorm\Test\Lifecycle;

use Anorm\Lifecycle\ChangeListenerInterface;
use Anorm\Lifecycle\DeleteListenerInterface;
use Anorm\Model;

class RecordingDeleteListener implements ChangeListenerInterface, DeleteListenerInterface
{
    /** @var array<int, array{model: Model, diff: array, isInsert: bool}> */
    public $writes = [];

    /** @var array<int, array{table: string, id: mixed, model: Model|null}> */
    public $deletes = [];

    public function onWrite(Model $model, array $diff, bool $isInsert): void
    {
        $this->writes[] = ['model' => $model, 'diff' => $diff, 'isInsert' => $isInsert];
    }

    public function onDelete(string $table, $id, ?Model $model): void
    {
        $this->deletes[] = ['table' => $table, 'id' => $id, 'model' => $model];
    }
}

Create `src/Lifecycle/DeleteListenerInterface.php`:

```php
<?php

namespace Anorm\Lifecycle;

use Anorm\Model;

/**
 * Opt-in companion to ChangeListenerInterface for deletions.
 *
 * Registered through the same slot, DataMapper::setChangeListener(). A listener
 * that wants both events implements both interfaces; existing write-only
 * listeners are unaffected.
 */
interface DeleteListenerInterface
{
    /**
     * Invoked once per DataMapper::delete() that removed at least one row.
     *
     * @param string     $table The table the row was deleted from.
     * @param int|string $id    The primary key value that was deleted.
     * @param Model|null $model The model, when the delete came through
     *                          Model::delete(); null for $mapper->delete($id).
     */
    public function onDelete(string $table, $id, ?Model $model): void;
}
```

- [ ] **Step 5: Wire the event into `DataMapper::delete()`**

In `src/DataMapper.php`, replace `delete()` and add `notifyDelete()` beside it:

```php
    /**
     * @param int|string $id    The primary key value to delete.
     * @param Model|null $model The model being deleted, when there is one. Passing it
     *                          lets a DeleteListenerInterface see which model went, and
     *                          clears that model's snapshot so a later write() is
     *                          correctly treated as an INSERT.
     * @return bool True when a row was deleted.
     */
    public function delete($id, ?Model $model = null)
    {
        $keyField = $this->map[$this->modelPrimaryKey];
        $sql = 'DELETE FROM `' . $this->table . '` WHERE `' . $keyField . '` = ?';
        $result = $this->query($sql, [$id], $model);
        // A bound primary key matches at most one row, so this is 0 or 1.
        $deleted = $result->rowCount() >= 1;
        if ($deleted) {
            $this->notifyDelete($id, $model);
        }
        return $deleted;
    }

    /**
     * Fire onDelete (when the listener opted in and we are not already inside one),
     * then drop the model's snapshot. Ordering matters: the listener runs first so it
     * can still read $model->_lastSnapshot for the pre-delete values.
     */
    private function notifyDelete($id, ?Model $model): void
    {
        $listener = self::$changeListener;
        if ($listener instanceof \Anorm\Lifecycle\DeleteListenerInterface && !self::$insideListener) {
            self::$insideListener = true;
            try {
                $listener->onDelete($this->table, $id, $model);
            } catch (\Throwable $e) {
                error_log('Anorm delete listener threw: ' . $e->getMessage());
            } finally {
                self::$insideListener = false;
            }
        }
        if ($model !== null) {
            $model->_lastSnapshot = null;
        }
    }
```

````markdown
## Delete events

`ChangeListenerInterface` covers writes only. To hear about deletions,
implement `DeleteListenerInterface` as well — on the same class, registered
through the same `setChangeListener` call:

```php
use Anorm\Lifecycle\ChangeListenerInterface;
use Anorm\Lifecycle\DeleteListenerInterface;
use Anorm\Model;

class AuditListener implements ChangeListenerInterface, DeleteListenerInterface
{
    public function onWrite(Model $model, array $diff, bool $isInsert): void
    {
        // ...
    }

    public function onDelete(string $table, $id, ?Model $model): void
    {
        error_log("Deleted $table #$id");
    }
}
```

The interfaces are separate so that existing write-only listeners keep
compiling. A listener that implements only `ChangeListenerInterface` is never
asked about deletes.

### What `onDelete` receives

- **`$table`** — the table the row was deleted from. Always present.
- **`$id`** — the primary key value that was deleted. Always present.
- **`$model`** — the model, when the delete came through `Model::delete()` or
  `Model::deleteOrThrow()`. It is `null` for `$mapper->delete($id)`, because
  the mapper knows the table and the map but not the model class.

If your listener needs the deleted row's values, delete through the model:

```php
$model->readOrThrow($id);
$model->delete();   // onDelete receives the populated model
```

### When it fires

`onDelete` fires only when the DELETE removed at least one row. A delete that
matched nothing is a no-op and produces no event.

Re-entrancy and exception handling match `onWrite`: a listener that deletes or
writes from inside `onDelete` is not re-invoked, and a listener that throws is
logged via `error_log` and swallowed.

### Snapshots

After a successful `delete()` that was given a model, that model's
`$_lastSnapshot` is set to `null`, so a subsequent `write()` on the same object
is correctly reported as an INSERT rather than diffed against a row that no
longer exists. The listener runs before the snapshot is cleared, so
`$model->_lastSnapshot` still holds the pre-delete values inside `onDelete`.
````

    public function readOrThrow($id)
    {
        $result = $this->_mapper->read($this, $id);
        if (!$result) {

        }
        return $result;
    }

    /**
     * Delete the row this model identifies.
     * The primary key property must be set — either read from the database or
     * assigned directly. Passing the model to the mapper is what lets a
     * DeleteListenerInterface see which model went.
     * @return bool True when a row was deleted, false when no row matched.
     * @throws \Exception if the primary key property is not set.
     */
    public function delete()
    {
        $key = $this->_mapper->modelPrimaryKey;
        $id = isset($this->$key) ? $this->$key : null;
        if ($id === null || $id === '') {
            throw new \Exception($this->modelLabel() . " cannot be deleted: primary key '$key' is not set");
        }
        return $this->_mapper->delete($id, $this);
    }

    /**
     * Short name for exception messages: 'Model' removed and the namespace
     * stripped, e.g. Anorm\Test\SomeTableModel -> SomeTable.
     * @return string
     */
    private function modelLabel(): string
    {
        $className = str_replace('Model', '', get_class($this));
        $tokens = explode('\\', $className);
        return end($tokens); // The last element: the class name without its namespace.
    }

## Notes for the implementer

**Why the injection test payload starts with `x`.** MySQL coerces a string to a
number when comparing it against an `INT` column. A payload starting with a
digit (`"1' OR '1'='1"`) coerces to `1` and would match the row with id 1, so
the bound and unbound versions would both delete something and the test would
be muddy. `"x' OR '1'='1"` coerces to `0`, matching no auto-increment id, so
bound deletes nothing and unbound deletes everything. MySQL raises a
`Truncated incorrect DOUBLE value` **warning** for the comparison, not an
error, so `PDO::ERRMODE_EXCEPTION` does not fire.

**`isset($this->$key)`** is the same idiom as `DataMapper::propertyValue()`. It
treats an unset property and a null one identically, which is what both
`delete()` and `deleteOrThrow()` want.

**Ordering matters in `notifyDelete()`.** The listener runs before
`$model->_lastSnapshot = null`, so a listener can read the pre-delete values
off the snapshot. Reversing those two lines breaks
`testDelete_ListenerSeesSnapshotBeforeItIsCleared`.

**Do not touch `read()` or `write()`'s id interpolation in this plan.** They
share the flaw and are tracked separately; changing them here would put an
unrelated regression surface into a security fix.
