# Delete Developer Experience — Spec

**Date:** 2026-09-20
**Status:** Approved for implementation
**Implements:** options A, B, E, G from the delete DX investigation (2026-09-20)
**Plan:** `docs/superpowers/plans/2026-09-20-delete-dx.md`

## 1. Problem

Deleting a record is currently spelled:

```php
$someModel->_mapper->delete($someId);
```

`DataMapper::delete()` (`src/DataMapper.php:483`) is the only delete path in
Anorm:

```php
public function delete($id)
{
    $keyField = $this->map[$this->modelPrimaryKey];
    $sql = 'DELETE FROM `' . $this->table . '` WHERE ' . $keyField . "='" . $id . "'";
    $result = $this->query($sql);
    // This allows for imprecise deletes which may not be the best idea. CP 25 Nov 2018
    return $result->rowCount() >= 1;
}
```

Four defects this spec addresses:

1. **`$id` is interpolated, not bound.** `query()` prepares the statement, but
   the id is already inside the SQL string by then. `delete("1' OR '1'='1")`
   deletes every row in the table. The published example in
   `docs/_docs/getting-started/crud.md:45` is literally
   `$id = 3; // Likely passed on via GET or POST`.
2. **No `Model::delete()`.** `Model` has `write()`, `read()`, `readOrThrow()`.
   Deleting is the only CRUD verb that forces consumers through `$_mapper`,
   the property `CLAUDE.md` designates as infrastructure.
3. **Deletes are invisible to the lifecycle listener.** `write()` fires
   `ChangeListenerInterface::onWrite()` and `readArray()` captures
   `Model::$_lastSnapshot`; `delete()` does neither. An audit consumer sees
   every insert and update and no deletions. A deleted model also keeps a
   stale `_lastSnapshot`, so a later `write()` is diffed as an UPDATE against
   a row that no longer exists.
4. **Silent false on a miss.** `delete()` returns `rowCount() >= 1`; deleting
   a non-existent id returns `false` with no way to opt into an exception,
   unlike the `read()` / `readOrThrow()` pair.

## 2. Scope

**In scope**

| Ref | Change |
|---|---|
| A | Bind the id in `DataMapper::delete()`; add a delete lifecycle event; clear `_lastSnapshot` |
| B | `Model::delete()` — no-argument instance method |
| E | `Model::mapper()` accessor; docs stop pointing consumers at `$_mapper` |
| G | `Model::deleteOrThrow()` |

**Out of scope** (considered and deferred)

- `QueryBuilder::delete()` / delete-by-Mango (option D) — separate plan.
- Soft delete (option F) — a policy Anorm has so far declined to have.
- `Model::delete($id)` with an optional id argument (option C) — rejected in
  favour of B; see §3.2.
- Binding the id in `read()` and the UPDATE branch of `write()`. They share
  the interpolation flaw but are non-destructive and touch far more
  behaviour (transformers, `dynamicWrapper` retry). Tracked separately.

## 3. Design decisions

### 3.1 The delete event needs a model, and `DataMapper::delete()` has none

`ChangeListenerInterface::onWrite(Model $model, array $diff, bool $isInsert)`
receives a model because `write()` is handed one. `delete($id)` receives only
an id, and `DataMapper` cannot construct a model: `createByClass()` derives the
table and map from a class but never stores the class name.

**Decision:** `DataMapper::delete()` grows an optional second parameter:

```php
public function delete($id, ?Model $model = null)
```

`Model::delete()` passes `$this`; existing `$mapper->delete($id)` call sites
keep working and pass `null`. The event therefore carries `(table, id, ?model)`
— the table and id are always available, the model only when the delete went
through `Model::delete()`.

### 3.2 Why no-argument `Model::delete()`

`Model::delete($id)` would read more conveniently for the "delete by id from a
request parameter" case, but it makes the listener contract ambiguous: with an
id the listener can only be told the id, without one it can be told the whole
model. Two semantics behind one method name leaks into consumer code.

The no-argument form keeps one meaning — *delete the row this model
identifies* — and consumers who have only an id pay one extra line, not an
extra SELECT:

```php
$model = new SomeTableModel();
$model->someId = $id;
$model->delete();
```

`$mapper->delete($id)` remains supported for the true one-liner case.

### 3.3 A separate `DeleteListenerInterface`, not a new method on `ChangeListenerInterface`

Anorm is released (latest tag `v3.1.2`). Adding `onDelete()` to the published
`ChangeListenerInterface` breaks every consumer that already implements it.

**Decision:** a new interface in the same namespace:

```php
namespace Anorm\Lifecycle;

interface DeleteListenerInterface
{
    public function onDelete(string $table, $id, ?Model $model): void;
}
```

Registration is a second static slot, `DataMapper::setDeleteListener()`.

> **Revised during implementation.** This section originally said registration
> would stay on the single existing slot, with `delete()` testing
> `self::$changeListener instanceof DeleteListenerInterface`. That does not
> compile: `setChangeListener()` is type-hinted to `ChangeListenerInterface`,
> so a delete-only listener can never reach the slot in the first place.
> Widening that parameter *and* the `getChangeListener()` return type would
> change two published signatures — the very thing §3.3 exists to avoid. A
> second slot is purely additive, and it spares a delete-only consumer from
> writing a no-op `onWrite()`.

A consumer who wants both events implements both interfaces on one class and
registers it on both slots. Consumers who want only writes are untouched. The
`$insideListener` re-entrancy guard is shared between the two hooks, so a
listener that writes from inside `onDelete` (or deletes from inside `onWrite`)
is not re-invoked.

### 3.4 Fire the event only on a successful delete

`onDelete()` fires only when `rowCount() >= 1`. An audit log should not record
deletions that did not happen. A `delete()` that matches no row is a no-op and
produces no event.

### 3.5 Event ordering and snapshot clearing

Order inside `delete()`, after the SQL succeeds and `rowCount() >= 1`:

1. Fire `onDelete()` (the model is still intact, `_lastSnapshot` still
   populated — a listener that wants the pre-delete values can read it).
2. Set `$model->_lastSnapshot = null`, when `$model !== null`.

Clearing the snapshot means a subsequent `write()` on that model is correctly
treated as an INSERT (`isInsert=true`), not an UPDATE against a vanished row.

### 3.6 Re-entrancy and listener exceptions match `write()`

`delete()` reuses the existing `self::$insideListener` guard, the same
`try/catch/finally` shape, and the same `error_log` on a throwing listener. A
listener that calls `write()` or `delete()` from inside `onDelete()` does not
re-invoke the listener; a listener that throws is logged and swallowed, and the
delete still counts as done.

### 3.7 `mapper()` is additive; `$_mapper` stays

`$_mapper` remains a public property — removing or renaming it breaks every
consumer and every fixture in `test/anorm/`. `mapper()` is added as the
documented accessor and the docs stop showing `$_mapper` to consumers.

### 3.8 `modelLabel()` is extracted, `readOrThrow()`'s message is unchanged

`readOrThrow()` builds its label inline (strip `Model`, take the last
namespace segment). `deleteOrThrow()` needs the same label, so the logic moves
to a private `Model::modelLabel()` and `readOrThrow()` calls it. The produced
message must stay byte-identical — `DataMapper_Crud_Test::testBogusReadOrThrow_MessageOk`
asserts `"SomeTable id '1' not found"`.

## 4. Public API after this change

```php
namespace Anorm\Lifecycle;

interface DeleteListenerInterface
{
    /**
     * Invoked once per DataMapper::delete() that removed at least one row.
     *
     * @param string     $table The table the row was deleted from.
     * @param int|string $id    The primary key value that was deleted.
     * @param Model|null $model The model, when the delete came through
     *                          Model::delete(); null for $mapper->delete($id).
     */
    public function onDelete(string $table, $id, ?Model $model): void;
}
```

```php
namespace Anorm;

class DataMapper
{
    // CHANGED: second parameter added, id is now bound
    public function delete($id, ?Model $model = null);

    // NEW: the delete listener's own registration slot
    public static function setDeleteListener(?DeleteListenerInterface $listener): void;
    public static function getDeleteListener(): ?DeleteListenerInterface;
}

class Model
{
    // NEW
    public function mapper(): DataMapper;
    public function delete();          // bool; throws if the primary key is unset
    public function deleteOrThrow();   // true; throws if the key is unset or no row matched
}
```

## 5. Behaviour

### `DataMapper::delete($id, $model = null)`

| Case | SQL | Returns | `onDelete` |
|---|---|---|---|
| id matches a row | ``DELETE FROM `t` WHERE `k` = ?`` bound to `$id` | `true` | fired |
| id matches no row | same | `false` | not fired |
| id contains a quote | same; the quote is data, not syntax | `false` | not fired |
| no delete listener registered | same | as above | not fired |
| called from inside a listener | same | as above | not fired (re-entrancy guard) |
| listener throws | same | as above | logged via `error_log`, delete still returns `true` |
| FK constraint violation | same | — | `PDOException` propagates unchanged |

When `$model !== null` and the call returned `true`, `$model->_lastSnapshot`
is `null` afterwards.

### `Model::delete()`

| Case | Result |
|---|---|
| primary key set, row exists | `true`; `onDelete` fired with the model |
| primary key set, no such row | `false`; no event |
| primary key `null` or `''` | `\Exception`: `"SomeTable cannot be deleted: primary key 'someId' is not set"` |

### `Model::deleteOrThrow()`

| Case | Result |
|---|---|
| row deleted | `true` |
| no such row | `\Exception`: `"SomeTable id '3' not deleted"` |
| primary key unset | `\Exception` from `delete()` (message above) |

## 6. Backward compatibility

| Existing usage | After |
|---|---|
| `$model->_mapper->delete($id)` | works unchanged; now bound and safe |
| `$model->_mapper` property access | works unchanged |
| `implements ChangeListenerInterface` | works unchanged; no new method required |
| `setChangeListener()` / `getChangeListener()` | signatures unchanged |
| An id that previously injected SQL | now deletes nothing and returns `false` |

The last row is the one intentional behaviour change, and it is the point of
the fix.

## 8. Constraints

- **PHP 7.4 syntax only** in `src/`. `composer.json` requires
  `^7.4 || ^8.0`. No constructor property promotion, enums, `readonly`,
  `match`, or PHP 8 string functions.
- **phpcs** PSR-12 + `phpcs.xml` (150 char lines in `src/`, short array syntax).
- **phpstan** level 5 over `src/` and `test/`.
- **Errors** go to `error_log`, not a `LoggerInterface` — existing precedent.
- Tests live under `test/anorm/`; underscored test class names are permitted
  there by `phpcs.xml`.
